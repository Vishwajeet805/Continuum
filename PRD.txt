# Continuum — Product Requirements Document v1

## 1. Product Goal

Continuum ka goal hai:

> Poor ya intermittent internet me digital service ko fail hone se bachana by finding and completing the **Minimum Viable Transaction (MVT)** — yani user ke task ka smallest safe, dependency-valid part jo current connectivity me complete ho sakta hai.

Main difference:

**Normal system:** full request complete karo ya fail ho jao.

**Continuum:** core intent secure karo, baaki later complete karo.

---

# 2. MVP Use Case

First prototype ke liye ek **Citizen Benefit Application Portal** banayenge.

User ko ek welfare/scholarship-type application fill karni hogi:

- Personal details
- Eligibility information
- ID proof
- Bank proof
- Photo
- Supporting document

Ye intentionally generic demo service hogi, kisi actual government portal ka clone nahi.

### Why this use case?
Because judges instantly samajh sakte hain:
> weak internet → form submit nahi ho raha → Continuum kya change karta hai.

# 4. MVP Definition of MVT

First version me MVT fully AI-generated nahi hoga.

Developer workflow configuration define karega.

Example:

```yaml
workflow: benefit_application

core_fields:
  - applicant_id
  - scheme_id
  - full_name
  - eligibility_status
  - created_at

deferred_fields:
  - profile_photo
  - id_proof
  - bank_proof
  - supporting_document
```

Core payload maybe:

```json
{
  "intent_id": "CNT-94F21",
  "applicant_id": "USR-123",
  "scheme_id": "SCH-101",
  "eligibility_status": true,
  "created_at": "..."
}
```

Ye MVT hoga.

# 5. Important Transaction States

Continuum ko state machine ki tarah design karenge.

```text
DRAFT
  ↓
SAVED_LOCAL
  ↓
INTENT_SECURED
  ↓
MVT_READY
  ↓
MVT_SENT
  ↓
SERVER_ACKNOWLEDGED
  ↓
CORE_COMPLETE
  ↓
DEFERRED_PENDING
  ↓
FULLY_COMPLETE
```

Error states:

```text
RETRY_PENDING
SYNC_FAILED
VALIDATION_FAILED
```

Important:

**Saved Locally != Server Acknowledged**

UI me ye clear dikhna chahiye.

# 8. MVT Engine

Ye project ka core hai.

Inputs:

```text
Workflow
+
Required dependencies
+
Payload sizes
+
Network budget
```

Output:

```text
Smallest safe executable transaction
```

First MVP algorithm simple rakhenge.

Pseudo logic:

```text
1. Load workflow.
2. Find required core transaction.
3. Calculate core payload size.
4. Estimate network budget.
5. If core payload fits:
      create MVT
   Else:
      save locally
6. Mark non-core data as deferred.
```

Later version me graph optimization add karenge.

# 10. Duplicate Protection

Very important.

Suppose user network issue ke wajah se 5 baar Submit click kare.

System ko 5 applications create nahi karni.

Har logical action:

```text
intent_id = CNT-...
```

Backend:

```text
if intent_id already exists:
    return previous result
```

Yani idempotent API.

# 23. Later Version — Real Algorithm

After MVP works, MVT ko graph model me move karenge.

Workflow:

\[
G=(V,E)
\]

Each node:

```text
size
required
dependency
atomicity
priority
```

Connectivity budget:

\[
B
\]

Find subset:

\[
S \subseteq V
\]

such that:

\[
\sum size(S) \le B
\]

and dependency constraints satisfied hon.

Goal:

> smallest dependency-complete safe checkpoint.

Ye project ka strongest CS/research component banega.
